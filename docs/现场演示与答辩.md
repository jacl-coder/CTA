# 现场演示与答辩

更新日期：2026-09-12。预计 10～15 分钟，可按评审关注点缩短。功能范围以[机试原题](机试题目-多品种期货交易风控系统.md)为准，核对入口见[交付与原题验收](交付与原题验收.md)。

## 演示前准备

完成安装后运行 `make run`，打开 `http://127.0.0.1:8004`。已打包时在解压根目录运行 `./dist/cta-risk/cta-risk serve`，同样只使用 `configs/default.yaml`。

首次默认“正常运行”，双源持续生成报价。顶部选择“手工演示”，点击“进入场景”；已在该场景时点击“重新开始当前场景”。全程保持同一终端和同一网址。

切换会新建独立数据，旧数据库和日报保留。关闭后再次启动会恢复上次场景。模拟交易日是演示业务日期；实际处理时间取自电脑北京时间。

## 第一段：工作台、账户与原题熔断场景（约 4 分钟）

选择“手工演示”后，说明尚未提交有效行情时不能交易。行情表单已填入三个初始价格：

1. 在“模拟交易”输入完整第 1 帧：螺纹钢 3500、铁矿石 800、IF 4000。
2. 提交账户 A、螺纹钢、多头、开仓 1 手。持仓由 2 手变成 3 手，手续费增加 2 元。在“持仓与成交”核对数量、成交来源和账户/品种筛选。
3. 返回交易页面，提交第 2 帧：螺纹钢 3400，其余价格不变。持仓浮亏 `(3400－3500)×10×3＝－3000`，等于初始资金 100000 的 3%。核对 A 熔断、开仓不可用，其他账户没有随 A 熔断。
4. 提交第 3 帧：螺纹钢恢复 3500，其余不变。浮亏回到零，但当日熔断保持。在“风险事件”查看告警进入、熔断和告警退出，不应出现第二次熔断。
5. 在账户总览勾选 A、B，打开“仅所选”，展示独立资金与风险对比。

解释后端实际拒单的证据：页面按钮禁用是用户提示；`demo_risk.py --packaged` 直接调用真实 HTTP 下单接口，验证拒单与成交数量不变，覆盖绕开前端的情况。需要现场演示接口拒单时，在开发环境运行该脚本即可，无需人为修改当前页面数据库。

## 第二段：逐日盯市与冻结日报（约 3 分钟）

进入“日结与日报”，此时已应用 3 帧，恰好达到本手工场景的收盘帧：

1. 点击“封账并停止交易”，说明开平仓均暂停；收盘行情不完整时不能清算。
2. 查看冻结结算价：螺纹钢 3510、铁矿石 810、IF 4005。强调结算价来自配置，允许与最后市场价不同。
3. 点击“按计划结算价清算”，展开 A 明细核对：期初 100000、平仓盈亏 100、剩余 3 手盯市盈亏 300、手续费 10，期末余额 `100000＋100＋300－10＝100390`；保证金 `3510×10×3×10%＝10530`。
4. 全账户期末余额应为 1299879，保证金合计 174150。下载 HTML，展示冻结的盈亏、敞口和风险状态。
5. 结转下一交易日，前日日报仍不变；次日尚无有效报价，账户不能交易。提交第 4 帧后可查看剩余持仓已作为昨仓，成本基准使用前日结算价，前日熔断已重置。

不要将这里的 A 余额与自动场景的 100292 混淆：本段额外开了 1 手，手续费与剩余持仓均不同。自动验收脚本的手算见[日结说明](日结与风控日报.md)。

## 第三段：两个行情源与中断恢复（约 2 分钟）

在页面顶部选择“故障与清算”，点击“进入场景”。自动进入行情监控，无需停止服务或更换网址。每秒一帧，约 96 秒完成：

- 第 8～20 帧源 A 中断：观察连接、连续接收和应用进度；业务暂停，源时钟继续推进。
- A 在第 10 帧下跌、第 15 帧反弹。恢复后补齐历史，风险事件仍记录第 10 帧触发，发现时间较晚，并带补数标识。
- 第 30～40 帧源 B 中断，第 32 帧触发 B 风险，第 36 帧反弹，恢复后同样补齐。
- 第 64 帧自动清算首日并结转，第 96 帧完成次日。未手工下单的场景中 A 首日余额 100292、次日余额 99892。

页面故障场景为 1000 ms/帧，两个源为独立进程；自动验收可缩短间隔。强制退出后端、单个源重启、逐项比较连续/故障结果的完整证据在交付包验证日志 `demo_market.log` 中。

## 故障与现场处理

- 源码方式的 `make run` 会正常停止本项目的冲突旧服务后启动。直接运行交付包可执行文件时，先在旧终端按 `Ctrl+C` 关闭原服务。若端口属于其他程序，换到未使用端口并对应修改浏览器 URL；双源主服务与两个源端口均要互不冲突。
- 价格过期：页面标注旧行情并禁单；手工场景提交合法下一帧。若已达到收盘帧，则进入封账清算，不继续追加本日帧。
- 启动后场景已经结束：说明恢复机制在工作。在页面点击“重新开始当前场景”。
- 文件导出失败：先检查当前阶段和冻结报告是否已提交，修复可写目录后点击“重新导出”，不会重复日结。
- 下单回包丢失：先核对原订单，或者重试同一编号与参数；不要新建重复委托。
- 当前运行配置冲突：恢复时使用原配置。需要改业务规则则新建运行，不改写已有账本。

## 答辩要点

### 为什么选 Python、SQLite 和 React？

本题重点是核算正确、行情容错和可交付。Python 的 Decimal 与测试工具适合独立手算核对；FastAPI/HTTPX 用于异步 I/O，React 展示账户表格和操作。SQLite 适合单机多账户事务，省去数据库部署。选择依据是当前有限负载；没有将 asyncio 当作 CPU 并行或声称已经完成高频生产性能验证。

### 两个模拟源是否真的独立？

是两个 HTTP 服务子进程，各自有端口、合约集合、历史和故障状态。它们共享可恢复的逻辑起点与冻结场景，是为了可重复地重现中断期间的价格变化。两个来源覆盖不同品种，因此缺少任一来源时，本项目选择暂停全局交易直到补齐完整帧。

### 为什么补数后不会漏掉熔断或重复触发？

先持久化原始来源帧并校验身份、序号与摘要，再组装同序号的全合约报价，按应用游标顺序推进。风险状态转换、应用游标和日志在同一事务提交。即使价格已经反弹，也不能跳过缺口内的亏损帧。熔断为当日保持状态，重放已经提交的相同输入不会新增一次状态转换。

### 单写者会不会成为瓶颈？

它保证行情、交易和日结在同一顺序中看到一致账本。同步 SQLite 操作在专用线程执行，事件循环负责 I/O；有界队列满时明确拒绝。当前没有压测吞吐承诺。扩大规模前应先测量队列等待、计算和提交耗时，再决定按运行或账户分片，跨账户事务也需重新设计。

### 3% 用的是哪一种亏损？手续费和已实现盈亏是否参与？

本项目按当前交易日基准计算剩余持仓浮动盈亏，取亏损额除以账户初始资金。手续费与已实现盈亏参与账户权益和日结，但不混入这个浮亏阈值。3% 是可配置的演示值；没有把权益回撤和浮亏混为一个规则。

### 净敞口为什么不能代替保证金和限制敞口？

多空相抵可能掩盖总持仓规模，所以限制采用单品种多空名义价值的绝对额之和；日报另列净敞口。保证金按账户、合约、多空方向核算，不跨账户对冲。具体计算口径与交易所规则不同之处已作为模拟设定说明。

### 为什么金额都用字符串？

输入时避免先经过二进制浮点，Python 用 Decimal 和显式精度/舍入规则计算，数据库及 API 保留十进制字符串。页面仅格式化展示，不用 JavaScript Number 重算金额；数量、序号、进度百分比使用整数或普通数值。

### 日结和次日平仓为什么不会重复计算盈亏？

日结将当日剩余持仓从当日基准盯市到结算价，余额随清算结转；次日基准更新为前日结算价，手续费和当日已实现值归零。昨仓平仓按这个新基准计算，前日已经结算的价格变化不会再次入账。

### 进程崩溃或者浏览器超时怎么处理？

订单编号和参数用于幂等，数据库事务提交完成后才发布内存状态。浏览器未知结果时保留原请求；重启用冻结配置和完整日志核对账本、原始帧、游标与报告。验证覆盖进程退出恢复，没有宣称整机断电和文件系统损坏均可自动修复。

### 报告输出与日结事务为什么分开？

日结先冻结数据库结果，HTML/JSON 是可重新生成的展示文件。磁盘写文件失败不回滚已经生效的清算，也不允许靠重新清算来修复导出；单独重试文件输出即可。

### 前端轮询是否会漏风控事件？

页面展示最新快照，可能看不到所有中间价格，但权威风险处理在后端逐帧执行。风险事件持久化并提供分页查询。采用轮询满足本题准实时展示，不需要让页面消费速度决定交易风险的处理速度。

### 哪些还没有做？

独立历史回放工具尚未实现；原题另三个附加项已接入。真实交易所、长期历史容量、生产负载、多用户授权和跨操作系统发行没有完成。本地可执行包验证使用当前 Linux 环境，目标机兼容性仍需实际确认。
