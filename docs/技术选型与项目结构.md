# 技术选型与项目结构

更新日期：2026-09-10

唯一外部需求来源：[机试题目 v20260703](机试题目-多品种期货交易风控系统.md)。[需求基线](需求基线.md)是本项目内部的原题索引。

本文确定下一阶段的技术方案、模块边界和开发顺序。技术选择与业务约定是本项目为落实题目作出的设计，不是题目额外规定的要求。本文描述目标实现，不代表代码已实现或验收通过。

Python 与 React 是用户选定的技术方向。SQLite、FIFO、事务组织、模拟帧协议和打包工具等属于内部实现选择，其保留或调整取决于是否有助于完成原题及可靠交付。后续任务先对应原题功能或交付条款，再说明采用何种技术措施。

实施进度：工程骨架已建立，持仓、估值与逐日盯市领域函数已通过两日手算样例；SQLite 账本、账户初始化、单写者应用服务与查询已接通，模拟价格驱动的风控下单及风险事务已验证，见[交易与风控闭环](交易与风控闭环.md)。详细范围见[测试方案](测试方案.md)及[账本接口与持久化](账本接口与持久化.md)。目录现状与依赖方向见[项目结构与开发约定](项目结构与开发约定.md)，启动方式见 [README](../README.md)。双源行情与恢复已按第 4 节接通，详见[双源说明](双源行情与恢复.md)。日结、跨日和日报已接通，见[日结说明](日结与风控日报.md)。附加展示与独立回放已接入，见[附加项验收](历史回放与附加项验收.md)。本地验证不代表机试方最终验收。

## 1. 总体方案

采用 **Python 3.12 + FastAPI + SQLite** 实现后端，采用 **React + TypeScript + Vite** 实现前端。代码按前后端分目录维护，发布时由后端托管构建后的前端资源，交付可执行程序及其运行文件。

后端保持模块化单体，同一个程序提供不同子命令：核心服务运行一个进程，两个模拟行情源分别运行在独立进程中；演示模式负责启动和退出这些进程。业务系统内部按行情、持仓、风控、清算、报表拆分模块。

核心范围覆盖 MD、POS、RISK、SET 全部要求。四项附加功能均纳入目标范围：配置化和可复现输入从底层支持，历史回放、仪表盘、多账户对比在核心闭环验收后实现。

主要优化围绕行情完整性、账户状态一致性、熔断实际拦截、逐日清算正确性和演示可复现性展开。

## 2. 技术选型及理由

### 2.1 Python + FastAPI：业务服务

- 使用 Python 3.12 实现行情接入、持仓、风控、清算、回放和命令行工具；使用 `uv` 管理 Python 环境与依赖，提交 `pyproject.toml` 和 `uv.lock`。
- FastAPI 提供 HTTP API 和 OpenAPI 描述；Uvicorn 运行服务，Pydantic v2 负责边界数据校验。
- HTTPX 异步客户端接入两个模拟行情源；标准库 `asyncio` 管理 I/O 并发，`argparse` 处理子命令，`logging` 输出包含运行、账户、事件标识的结构化日志。
- 领域模型使用带类型标注的 dataclass、枚举和 Decimal，不依赖 FastAPI。规则与清算写成可直接测试的函数和状态转换。
- 当前使用 Python 3.12.3、uv 0.11.14，依赖已锁定并完成基础服务、React 页面与账本迁移资源的打包验证；现有版本不代表最新版本，后续模块仍需各自验证。

选择理由：题目重点是计算正确性、容错及工程交付，Python 方便编写清算样例、规则测试和历史回放，FastAPI 也方便联调展示接口。当前模拟负载适合先采用此方案，但实际性能仍需测试；`asyncio` 用于 I/O 并发，不代表 CPU 计算会自动并行。

### 2.2 SQLite：持久化与事务

- 使用 Python 标准库 `sqlite3`，以明确 SQL 和编号迁移文件管理数据。事务和核算写入路径直接可读。
- 启用 WAL、外键、唯一约束和事务，配置忙等待超时；业务写事务通过单一写入路径串行执行。
- 金额与价格存为规范十进制字符串，数量和序号用整数；金融求和在 Python 业务层执行，避免 SQLite 隐式浮点转换。

选择理由：单机多账户需要可靠事务和核算隔离，SQLite 可以满足且无需单独部署数据库。标准库驱动减少运行依赖；数据库连接、事务和迁移集中在存储适配层管理。

### 2.3 Decimal：金额与风险计算

- 使用标准库 `decimal.Decimal` 处理价格、金额、保证金率和风险比例。
- JSON、配置、数据库中的十进制值通过字符串解析，边界拒绝二进制浮点输入、NaN 和 Infinity，避免在进入 Decimal 前丢失精度。
- 中间计算采用显式 `localcontext`，精度为 38 位，超出精度时拒绝静默舍入；人民币入账使用 `quantize` 与 `ROUND_HALF_UP` 按分舍入。手续费按成交舍入，平仓、盘中浮盈亏与结算盈亏按批次明细舍入后汇总，保证金按合约及多空方向合并数量后舍入。当前输入范围与样例见[业务口径](业务口径与计算样例.md)。
- 价格按最小变动价位校验；风控比较使用业务值，不能使用页面格式化后的截断值。

选择理由：明确精度和舍入边界，使阈值、清算明细与账户汇总能够通过独立样例复核。

### 2.4 YAML：参数与合约配置

- 使用 PyYAML 的安全加载器并增加重复键检查，再由 Pydantic 执行严格字段及业务校验。金额、价格和比例在 YAML 中写为带引号的十进制字符串，不能先被加载为 float。
- 配置覆盖账户、合约规则、交易日和会话、行情源、风险阈值及输出目录。
- 启动时拒绝未知字段、重复标识、非法比例和缺失规则；保存配置快照及哈希，供日报和回放追溯。
- 首版修改配置后重启生效，不做热更新；恢复已有交易日要求配置一致，新配置用于新的运行或下一交易日。

该选择直接覆盖 EX-03，并避免运行中修改计算参数导致前后口径不一致。

### 2.5 React + TypeScript：监控与操作界面

- 使用 React、TypeScript、Vite 和 Ant Design。React 组织页面与交互，TypeScript 约束数据结构，Vite 提供开发和构建，Ant Design 提供账户表格、表单、状态提示等组件。
- 使用 npm 管理依赖，提交 `package-lock.json`，通过 `npm ci` 安装。当前环境已核实有 Node 24.19.0、npm 11.17.0；React、Vite 等版本在实施时选择兼容组合并锁定，不使用浮动 latest 作为构建依据。
- 开发时 React 运行在 Vite 服务，通过代理访问后端 `/api`；发布时 FastAPI 托管 `frontend/dist` 的构建产物，API 和页面同源，运行机无需 Node 或前端开发服务器。
- HTTP 提交命令，每次工作台快照请求结束后等待 500 ms 再刷新；断线恢复后重新获取完整快照，连接状态必须可见。本阶段以轮询替代早期 SSE 设计，详见[前端接入](前端工作台接入.md)。后端更新是账户数据的权威来源，前端不自行重算盈亏或决定交易放行。
- 页面包括账户总览、多账户对比、持仓、风险事件、行情源状态、模拟开平仓和日报查看。路由使用 React Router，页面状态使用 React hooks 和 Context。
- 金额与价格在 API 中保持字符串，在输入、传输和展示过程中保留精度；不能使用 JavaScript Number 计算金融结果或修改风险状态。若后续画图需要数值转换，仅用于可视化坐标，精确值仍由后端提供。
- FastAPI OpenAPI 作为 API 契约，使用 `openapi-typescript` 生成前端类型；生成文件纳入版本控制，接口变更后重新生成并检查差异。Decimal 的字符串协议需在响应模型中显式体现。

选择理由：React 与现成组件适合本题多账户表格、状态更新和表单操作，也便于现场展示。全部前端资源随发布包提供，无 CDN 依赖。首版不把复杂图表作为前置条件。轮询页面展示最新快照，核心风险链路仍逐帧处理完整有效行情并记录风险事件。

### 2.6 日报、测试和可执行交付

- 日报读取冻结日结快照，当前采用标准库 HTML 渲染与 `html.escape` 转义，生成含本地样式的独立 HTML 并导出 JSON；离线日报不依赖 React 服务。固定格式无需模板引擎，因此调整了早期 Jinja2 选型。
- 后端采用 pytest、pytest-asyncio、HTTPX 测试，使用临时 SQLite、可控时钟、固定输入和真实进程重启验证。
- Ruff 负责格式与静态检查，mypy 检查类型。前端使用 TypeScript 类型检查、ESLint、Vitest 和 React Testing Library，重点验证断线状态、拒单原因及服务端数据展示；本阶段通过实际浏览器操作验收，持久化 Playwright 测试套件尚未建立。
- 计划检查后端 `ruff check`、`ruff format --check`、`mypy`、`pytest`，以及前端类型检查、lint、单元测试、生产构建和关键端到端演示。并发与恢复由受控场景验证，不把静态检查当成竞态验证。
- 使用 PyInstaller 的 `onedir` 模式生成包含解释器与依赖的可执行发布目录，将前端构建产物、日报模板和 SQL 迁移一起打包；交付整个目录压缩包，不只复制其中的启动文件。
- 先运行前端锁定安装与生产构建，再同步资源到后端包，最后打包；资源缺失直接构建失败。业务数据、配置和报表写入可写运行目录，不能写入包内资源目录。
- `Makefile` 提供便捷入口，文档也给出原始 uv/npm 命令。首个目标为 Linux amd64，在目标平台构建并验证；Windows 等平台需独立构建测试，不承诺跨平台通用可执行文件。

可执行交付是题目要求。需在没有项目虚拟环境、没有预装 Python/Node 的目标兼容环境中启动发布包并完成演示，不能仅用源码启动成功代替打包验收。PyInstaller 仍受目标系统和运行库兼容性约束，交付记录应注明验证环境。

## 3. 架构与状态更新顺序

```text
模拟行情源 A ─┐
              ├─ 接入/校验/原始数据存储 ─ 完整行情帧 ─┐
模拟行情源 B ─┘                                     │
                                                    ▼
HTTP / 场景脚本 ─ 开平仓命令 ──────────────── 业务事件循环
                                                    │
                                   持仓估值 → 风控检查
                                   成交入账 → 持仓更新
                                   收盘封账 → 清算入账
                                                    │
                                   SQLite 事务提交与快照
                                                    │
                                   HTTP 快照 → React
                                   导出器 → HTML/JSON 日报
```

一个业务事件循环拥有全部可变账户状态。行情接入与 HTTP 可以并发，通过有界入口提交消息，不能直接修改持仓、余额或熔断状态。

具体采用单个 Uvicorn worker，FastAPI lifespan 启停一个引擎协程，HTTPX 行情任务和 API 通过 `asyncio.Queue(maxsize=...)` 提交命令。业务状态只由引擎协程修改；禁止通过增加 Uvicorn workers 复制多个状态所有者。API 超时或客户端断开后，已接收命令仍由引擎管理，客户端通过幂等键查询最终结果，不能把网络超时等同于未成交。

SQLite 连接在专用单线程执行器中创建和使用，一整个事务作为一个工作项执行；引擎等待提交完成才发布状态。数据库工作项入口也需有界，不能依赖执行器默认的无限队列。HTTP 查询主要读取已发布快照，历史查询通过受控存储入口执行。不能把同步数据库和报表文件 I/O 直接放进异步请求循环造成长时间阻塞。

开仓处理顺序为：参数与幂等检查 → 账户状态检查 → 按当前有效行情计算开仓后的持仓与保证金 → 放行或拒绝 → 模拟执行生成成交 → 更新持仓与风险 → 事务提交 → 发布快照。首版模拟执行同步且确定，不存在异步挂单余额预占窗口。

业务层先生成待提交的新状态，数据库成功提交后才替换内存状态、确认请求并发布。失败不修改已发布状态；持久化不可用时拒绝新的业务写操作，重启以已提交记录恢复。

成交、持仓变更、账户更新及其引发的风险状态在同一事务中提交。拒绝命令也留下记录。两个并发开仓命令按确定顺序检查，后一个看到前一个更新后的账户。

核心消息不静默丢弃。入口满时交易请求返回明确繁忙错误；行情客户端停止本次消费并从持久化连续游标补拉。页面通过独立快照通道更新，不阻塞核心处理。

## 4. 两个行情源及恢复方案

### 4.1 数据源与覆盖范围

两个独立模拟服务读取可复现价格场景，各有源标识、序列号、连接和补拉接口：源 A 提供 SHFE 螺纹钢示例合约；源 B 提供 DCE 铁矿石和 CFFEX 股指期货示例合约。

演示使用至少 3 个策略账户和上述 3 个品种的具体合约，账户可跨两个源持仓。合约与品种标识分开维护。乘数、最小变动价位和保证金率通过配置给定并标明演示规则，不冒充交易所当前官方参数。

两个源使用相同协议、覆盖不同合约，均通过实际 HTTP 接入，均支持单独断线、延迟和重复发送。采用分工覆盖满足多源要求，不增加同一合约跨源仲裁逻辑。

模拟源可在无外网环境下复现亏损、恢复和清算，且完整历史可核对。它验证业务与接入逻辑，不证明真实交易所连接能力。

### 4.2 协议与有序推进

- 默认持续工作台每 1000 ms 推进一帧，固定验收场景每 250 ms 一帧，均可配置速度。每帧包含该源负责合约的价格集合，源进度接口另含场景结束标记，没有价格变化也提供完整帧。
- 帧字段包括 `run_id`、`source_id`、`trading_day`、连续 `sequence`、`event_ms`、价格字典和内容摘要；风险事件另记发生时间、检测时间及恢复发现标记。
- 当前实现使用 HTTP 有界轮询：`/head` 获取最新帧，`/history` 按连续序号分段补拉。历史由冻结场景和起点确定性重建，独立于客户端连接，断线时逻辑序号继续推进。此选择替代早期 NDJSON 长连接设计，满足原题允许自行设计更新频率与格式的要求。
- 两源共享运行标识和逻辑帧时钟。引擎按递增帧号应用已收齐两个源数据的完整帧；同帧先统一更新价格并评估风险，再执行交易命令。
- 交易日志修订号记录命令顺序，订单结果记录使用的价格帧。完整行情按逻辑序号处理，源数据的网络到达顺序不改变风险处理顺序。

演示启动器向两个源传入相同的场景、开始时刻与运行标识；源重启恢复其历史和序号，不能在同一运行中从零重用序号。跨日场景用显式会话边界决定帧交易日，序号贯穿整个运行。首版运行采用有限固定场景，源可重建全部演示帧的历史，补拉接口明确返回连续范围和结束游标。

交易命令按应用队列顺序执行，并记录所使用的完整帧；执行时若行情无效，立即保存拒单结果，不等待未来行情或插入历史帧。HTTP 等待超时后按幂等键查询最终结果。模拟故障按帧定义，测试注入可控时钟；实时交易还要求应用进度追平逻辑当前帧，历史补数不能刷新成可交易行情。有限场景结束后显示结束并停止交易，启用清算计划时按会话边界执行封账、清算和下一交易日处理。

这是针对可控模拟环境选择的顺序模型，使历史价格和当时持仓保持一致。真实交易所源不天然共享帧号，未来替换时必须重新设计事件时间与迟到成交处理。

### 4.3 缺失、去重与恢复

1. 验证源、合约、序号和价格后落库。唯一键为运行、源和序号；相同键相同内容忽略重复，相同键不同内容视为数据错误并暂停推进。
2. 序列缺口、帧缺失或 HTTP 观测失败触发恢复，保留最后完整业务帧，补拉缺失区间。
3. 可以保存后续到达帧，但不能越过缺失帧修改账户状态。恢复期间暂停全局模拟交易，新开平仓命令明确返回数据恢复中；不改变已经提交的成交。
4. 补齐后按帧估值和计算风险。先前未处理过的历史阈值穿越仍产生事件，即使最新价格已反弹也不能漏掉；记录发生帧、检测时间及恢复发现标记。
5. 风险事件使用运行内递增事件编号，保留账户、触发帧和转换类型；通过原始帧唯一键、按序应用及状态转换保证幂等。应用游标、风险日志和事件追踪信息共同提交，重复补拉或重启不重复执行转换。
6. 积压完整帧处理完且行情新鲜度合格后恢复交易。历史不能补齐时保持不可交易并显示连续接收与应用进度及阻止原因，不伪造价格。

首版接受“一源缺失时暂停全局模拟交易”的可用性代价，简化跨源账户一致性。多账户独立核算仍成立；按账户隔离行情故障属于后续优化。

只保留最新价格会漏掉中间亏损触发点，因此恢复链路必须处理完整有效序列。展示快照可以合并，核心风险计算不能照搬这一策略。

## 5. 业务实施约定

### 5.1 持仓与模拟交易

- 持仓来自模拟成交，以及带来源标识和幂等键的初始化导入。导入仅允许在交易日前初始化阶段，不提供绕过风控的运行中开仓导入。
- 多空独立保存，反向开仓不自动抵销；开平意图显式传入，平仓不能超过可平数量。
- 保留持仓批次、今昨仓、开仓价和当前结算基准。平仓指定今仓或昨仓，类别内按 FIFO 消耗；数量不足拒绝，不隐式改变类别。
- 默认按有效最新价全部模拟成交，不模拟盘口排队、部分成交和滑点。手续费支持每手固定金额配置，标明演示值。
- 账户和合约构成持仓核算维度，品种查询通过元数据汇总。敞口分别展示多头、空头、净额与绝对额，避免净额掩盖总持仓。

### 5.2 首版风险规则

- **资金维度**：持仓当日浮亏达到初始资金的 2% 告警，达到 3% 熔断，均为可配置演示默认值。
- **持仓维度**：单品种总名义敞口超过账户配置额度，限制新增开仓；额度按账户、品种配置。同品种各合约、多空仓分别计算绝对名义金额再求和。开仓前同时检查预计敞口，超过额度直接拒绝，不能先成交再补做限制。
- **资金检查**：预计开仓后可用资金不足，拒绝该笔开仓；页面和日报展示权益、当日已实现盈亏、浮盈亏与保证金。
- **熔断行为**：当日锁存，反弹不自动解除；禁止开仓，有有效行情且系统可交易时允许平仓，不自动强平；首版无当天人工解锁入口。
- **跨日行为**：前日清算成功、账户与行情校验通过后清除上一日亏损熔断，并重新检查当前规则。数据恢复、敞口超限和资金不足等其他原因仍可限制开仓。
- **状态与事件**：各阻止原因独立保存。告警按状态进入记录一次，退出再进入可生成新事件；亏损熔断同一交易日只进入一次。解除敞口限制不能顺带解除熔断。

“持仓当日浮亏”定义为所有未平仓批次当日浮盈亏求和后的负值部分：昨仓以昨结算价为基准，今仓以开仓价为基准。不混入已平仓盈亏；当日总盈亏另行展示。

### 5.3 逐日盯市

方向 `d` 为多头 +1、空头 -1，数量 `q`，乘数 `m`，最新价 `P`，当日结算价 `S`，批次当日基准 `B`。昨仓 `B` 为昨结算价，今仓 `B` 为开仓价。

```text
未平仓盘中浮盈亏 = d × (P − B) × q × m
当日平仓盈亏     = d × (平仓价 − B) × 本次平仓数量 × m
剩余仓位结算盈亏 = d × (S − B) × 剩余数量 × m

当日净盈亏 = 平仓盈亏合计 + 剩余仓位结算盈亏合计 − 手续费
期末结算余额 = 期初结算余额 + 当日净盈亏
盘中权益 = 期初结算余额 + 平仓盈亏合计 + 当前浮盈亏合计 − 手续费
保证金 = 各多空仓分别按 abs(数量 × 估值价格 × 乘数) × 保证金率求和
可用资金 = 权益 − 保证金
```

盘中保证金使用最新有效价格，清算使用结算价；首版多空分别计提，不做组合优惠。保证金是资金占用，不是费用，不从权益重复扣除。交易日内不提供出入金，初始资金与每日结算余额分别保存。

清算使用独立结算价输入，演示由场景文件提供，不默认用末笔行情替代。缺少所需结算价、行情仍有缺口或未封账时，清算失败并说明原因。

交易日与会话来自配置，事件携带 `trading_day`，夜盘不能简单按自然日切换。模拟日历随场景提供，不宣称覆盖全部真实节假日。

收盘进入 `CLOSING`，停止接收新的当日交易，处理完截至收盘帧的有效数据后封账。定时器发出清算命令，同时提供相同入口供手动演示和失败重试。全部账户日结在一个事务内保存结果、明细、结算价和配置哈希；剩余仓位以当日结算价重置基准，转为下一交易日昨仓。

每账户每交易日结果唯一。同输入重复清算返回已存结果，输入变更拒绝覆盖，历史更正不纳入首版。报表读取冻结日结快照，写文件失败可重试，不重复入账。

实现前用手算样例固定两日昨仓、今仓开平、部分平仓、费用和保证金结果，测试不得仅用实现自身生成预期值。

## 6. 存储及接口边界

主要实体：

- `runs`、`config_snapshots`：运行模式、场景、版本、配置。
- `accounts`、`instruments`：账户及合约规则。
- `market_frames`、`source_cursors`：原始帧、哈希、连续接收进度。
- `commands`、`trades`、`position_lots`：命令及拒绝原因、成交、持仓批次。
- `account_states`、`risk_events`、`engine_checkpoints`：余额与限制原因、风险转换、已应用帧。
- `settlements`、`settlement_lines`：账户日结及明细。

实体带运行标识；规则回放使用独立内存状态，结果由页面下载，不写在线数据库。接收游标与应用游标分开，不能把已收到当作已完成风险处理。幂等命令使用运行与账户范围内的请求键；同键同参数返回原结果，同键不同参数拒绝。

API 围绕账户与品种查询、源状态、模拟开平仓、风险事件、清算及报表组织。处理器只校验输入、调用应用层和返回结果，具体 URL、DTO 和错误码在实施时补入接口文档。

默认绑定回环地址，写操作使用启动生成的会话凭据并检查同源请求。健康检查区分进程存活与业务可交易。外部多人访问、权限体系、TLS、真实交易网关和交易所规则核验属于实际部署前需补齐的能力，本地演示通过不等于生产验收完成。

## 8. 回放、演示与交付入口

回放输入为初始化账户/持仓、行情帧、按发生顺序保存的交易命令、结算价、会话和配置快照。后端顺序计算完整结果，前端支持播放、暂停、上一步、下一步和拖动查看；业务日期来自历史输入。输出风险事件、拒单、账户和日结，用于验证规则；不承担策略研究或真实成交质量评估。

仪表盘复用查询快照，显示各源进度、最后完整帧、新鲜度、账户权益/盈亏/敞口/保证金及全部交易阻止原因。恢复中不能把旧价格标为当前有效行情。

当前已实现的入口如下；`serve` 加载双源配置时自动启动两个源。独立源子命令通常由托管启动器调用，传入数据库中保存的逻辑起点：

```text
uv run --project backend --locked python scripts/demo_market.py
cta-risk serve --config testdata/configs/market-demo.yaml
cta-risk market-source --config testdata/configs/market-demo.yaml --source-id source-A --epoch-ms <逻辑起点>
cta-risk check-config --config testdata/configs/market-demo.yaml
```

日结与日报当前通过 `uv run --project backend --locked python scripts/demo_settlement.py`、`make run CONFIG=testdata/configs/settlement-demo.yaml` 和 `/api/settlement/*`、`/api/reports/*` 操作。独立回放通过同一工作台的 `/replay` 页面操作，API 为 `/api/replay/example`、`/api/replay/current`、`/api/replay/validate`、`/api/replay/run`，无需增加启动配置。

源码开发时在仓库根目录通过 `uv run --project backend cta-risk ...` 调用同一入口，前端在 `frontend` 中运行 `npm run dev`。发布后直接执行发布目录中的 `cta-risk`。包资源通过统一资源定位层读取，必须同时验证源码模式和 PyInstaller 模式；独立模拟源的子进程启动也需兼容两种模式。

`uv run --project backend --locked python scripts/demo_market.py` 使用临时运行启动两源和业务服务并验证后清理；日结演示脚本调用运行服务的清算入口，不另开进程直接改同一数据库。手动重复演示使用新运行目录或明确恢复已有运行，不默认删除数据。

交付包包含目标平台可执行目录、配置、场景、技术与使用文档、测试方案和结果、部分代码截图。React 构建资源、日报模板和迁移随运行包分发。现场验证至少覆盖启动、页面刷新路由正常、熔断后实际拒单、两源分别恢复、两日清算和离线日报打开；运行截图或视频按时间准备。

## 9. 开发阶段与完成条件

按一周期限安排以下顺序，具体日期服从实际机试起止时间：

1. **核算基础**：建立 Python 后端与 React 前端工程、配置和迁移，固定两日手算样例，完成持仓、估值、清算计算测试。及早验证包含最小 React 页面、SQL 资源与模拟源子进程的 PyInstaller 包能启动，降低最终交付风险。对应 POS、SET-01、DEL-02。
2. **交易与风控闭环**：完成事件循环、模拟执行、规则与事务；验证 3% 熔断、拒绝开仓、有效平仓、并发不绕过检查、多账户独立核算。对应 POS、RISK。
3. **双源与恢复**：完成独立模拟源、完整帧、补拉、去重、重启恢复；验证断线期间跌破阈值后反弹仍触发正确熔断，重复恢复不重复产生事件。对应 MD、RISK-04。
4. **日结与日报**：接入封账、清算事务、跨日及 HTML/JSON 导出；验证重试不重复入账和报表一致性。对应 SET。
5. **附加能力**：完成回放、React 仪表盘、多账户对比，验证配置无需改代码；核对 API 生成类型、轮询重连快照及拒单提示。对应 EX-01 至 EX-04。
6. **交付验证**：独立目录按说明构建启动，运行测试和演示，记录版本、结果与限制，准备可执行包及文档截图。对应 DEL。

每阶段以测试和演示通过为完成依据。时间不足时优先保证核心与交付材料，缩减页面修饰和附加细节，不降低恢复、风控、清算正确性。

## 10. 关键测试与性能证据

- 两源都参与估值，分别断线、延迟、重复、同序号冲突及历史缺失，结果可解释。
- 在故障窗口不提交新交易、其余输入相同的样例中，连续运行与中断补回得到相同账本和风险触发帧，检测时间允许不同。另测故障窗口开平仓请求被拒绝且无成交；这一场景与正常运行的成交结果可以不同，不要求错误地保持一致。
- 熔断阈值以下、恰好达到和超过；补回时不漏中间穿越，平仓降低浮亏不解除已锁存熔断。
- 多空、今昨仓、部分平仓、超量平仓、重复命令、多账户同品种及并发开仓。
- 两日盯市、平昨和平今、费用舍入、保证金不重复扣权益、基准重置、报表与余额核对。
- 缺失结算价、重复日结、变更输入、日结事务失败和报表写入失败。
- 提交前后进程退出、展示轮询延迟、队列满、配置不一致恢复。
- Python 事务提交期间客户端取消或网络超时后的幂等查询；React 页面刷新、轮询断线恢复、金额字符串精度、表单提交结果与后端状态一致。
- PyInstaller 发布目录在目标兼容环境中启动两源、服务和 React 页面，不依赖开发用虚拟环境或前端服务。

默认持续工作台为 3 账户、3 合约、每秒 1 帧；固定验收场景每秒 4 帧。性能验证记录指定负载下的处理耗时、积压、内存和恢复用时，不将未经测量的数字写成已实现能力。
