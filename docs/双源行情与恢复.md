# 双源行情与恢复

更新日期：2026-09-10。唯一外部依据是[机试原题](机试题目-多品种期货交易风控系统.md)。本阶段落实至少两个行情源、准实时更新、中断恢复补全和风险信号一致性；协议、时钟、故障窗口和全局暂停策略均为本项目自主设计。

## 数据源与选择理由

使用两个独立的本地 HTTP 服务进程：`source-A` 提供 SHFE 螺纹钢，`source-B` 提供 DCE 铁矿石和 CFFEX 股指期货。各源有独立端口、连接、超时及故障窗口，通过 HTTPX 并发轮询接入。两个源分工覆盖不同合约，配置校验要求覆盖全部账本合约且不重叠。

采用模拟源是为了在没有交易所凭据、没有外网的环境下演示，并精确复现“中断期间亏损越线、恢复前价格已经反弹”的验收场景。合约参数是演示配置，不代表交易所最新规则。源服务不读取或写入账本数据库。

固定验收模式使用关键帧价格：关键帧之间延续上次价格，但每个逻辑序号仍有完整报价。第一次启动将场景及共享逻辑起点 `epoch_ms` 存入 SQLite，两个源使用同一起点，默认每 250 ms 生成一帧。逻辑时间独立于 HTTP 连接；中断或源进程退出期间，行情序号仍随时间推进。

历史通过冻结场景、起点和序号确定性重建，可覆盖整个有限演示场景，无需源进程持续在线写历史文件。源重启不会从零重新编号，后端重启不会重新播放一个新场景。这是可控模拟环境的历史实现；真实行情适配需要另行实现可追溯的历史接口和事件时间协调。

## 持续行情验收配置

`configs/live-demo.yaml` 用于持续行情自动验收，主服务监听 8004，独立源监听 8301/8302。每秒一帧，首帧使用配置初始价格；后续价格在初始价上下 20 个最小变动单位内波动。每 16 帧选择一个由固定种子、源、合约和节点序号决定的价格节点，节点间按整数 tick 插值。生成单帧不依赖之前的调用顺序，也不依赖进程内随机状态。

`market.continuous: true` 时，`frame_count` 表示每个模拟日的帧数（默认 1800），不限制总运行帧数。全局序号不重用，`/head` 不再因为达到该帧数而标记结束。`market.sessions` 与 `settlement.days` 各提供一个首日模板，`settlement.repeat_daily: true` 和 `auto_settle: true` 配套启用。配置校验拒绝持续行情与有限清算计划混用。

每 30 分钟结束一个模拟交易日。连接中断不停止时钟；即使跨越多日，也逐日补齐、清算、结转，不能跳过历史风险或把昨日行情当今日报价。结算价来自显式模板，每日重复；这是演示假设。日期连续递增，包含周末，不映射真实交易所日历，也不模拟换月。

首次连接成功并应用完整帧后即可交易。正常退出后再次运行会保留成交、持仓、风险和日报；补齐停机缺口并收到新帧后恢复交易。修改种子、价格生成规则、日长或结算价须使用新的运行标识及数据库，不能改写已有事实。

持续模式的已应用原始历史保留在 SQLite，热缓冲仅保留末个已应用帧和待处理帧，避免每次轮询扫描全部已应用原始历史。启动仍完整核对原始行情及交易日志，按序号建立临时索引核对完整帧。交易帧、订单、事件及数据库会随运行增长；本次支持持续演示，不承诺无限磁盘、恒定内存或长期生产运行性能。

固定关键帧、故障窗口及 16/24 秒验收场景保持原有行为；手工输入行情使用 `make new-demo`。

## 协议与接入顺序

采用有界 HTTP 轮询及分段补拉。早期目标设计中的 NDJSON 长连接已调整为这一实现，原题允许自行设计格式和频率。

- `GET /head`：返回运行、源标识、起点、当前序号、结束标记和最新帧；开始前序号为 0，最新帧为空。
- `GET /history?start=1&end=20&limit=16`：返回连续范围、当前源进度及下一补拉序号；单次最多 256 帧，请求未来范围返回 409，非法范围参数返回 422。
- 每帧携带 `run_id`、`source_id`、`trading_day`、`sequence`、`event_ms`、价格字典和 SHA-256 内容摘要。价格用十进制字符串传输。
- 源故障窗口内返回 503，可配置响应延迟验证超时。有限窗口在场景结束后失效，仍可读取最后一帧和完整历史。

接入适配器校验源身份、起点、范围、摘要和帧内容，将原始数据交给应用队列持久化。模拟适配还会核对冻结场景，拒绝错误价格、未来帧或不匹配的合约。原始数据以 `(run_id, source_id, sequence)` 唯一；相同数据重发只增加本次进程的重复计数，相同键内容冲突拒绝。

原始接收与业务处理采用两套进度：每源的最高连续接收序号从持久化原始行推导，运行的 `applied_sequence` 表示已经完成风控处理的完整帧。收到序号 20 并不意味着 1 至 19 已齐全。

任何源发生缺口或不可用时，仍可保存另一源的后续数据，但只按递增序号合并两源都齐全的帧。每轮补拉和处理有批量上限，缺口未补齐就继续下一轮。补拉会适当重叠一个已有序号，用同一套幂等校验处理网络重试。

## 风险与交易顺序

完整价格帧、订单及原始行情均复用 `LedgerService` 的有界队列和唯一消费者。行情适配器、源进程与 API 都不直接修改账户或风险状态。

完整帧依次估值并执行原有风险规则；风险日志、应用游标和本次新事件的追踪信息在同一 SQLite 事务中提交，再发布内存状态。事务失败保留此前已提交状态，停止业务写入；重启从原始行情和交易日志恢复后重试。

缺口、断线和补数期间暂停全局新开平仓，订单保存 `MARKET_UNAVAILABLE` 拒绝结果，不产生新成交。追平全部源、连接健康、当前逻辑帧已经应用且价格有效后恢复交易。判断在执行订单时再次进行，不能将“刚收到的旧历史帧”当成实时行情。

恢复按历史顺序处理每一帧，不能只计算重连后的最新价。风险事件保留原有发生帧，并增加：

- `occurred_ms`：触发帧的逻辑发生时间。
- `detected_ms`：实际执行风险转换的时间。
- `recovered`：本次事件是否在恢复处理期间发现。

手动价格和订单引起的事件没有上述行情追踪值，返回 `null`。恢复标记描述发现过程，不改变阈值判断。告警可以进入、退出再进入；当日熔断仍只触发一次，反弹不清除。重复原始帧不再次应用，重启也不重复产生已提交事件。

## 结构与恢复校验

- `domain/market.py`：不可变场景、源帧、逻辑序号及确定性历史生成。
- `config/market.py`：覆盖范围、价格、端口、频率及故障配置校验。
- `simulator/server.py`、`simulator/launcher.py`：独立 HTTP 服务与托管进程启停、自动重启；后端被强制结束时，源检测父进程退出并结束自身。
- `marketdata/protocol.py`、`marketdata/client.py`：网络格式、并发观测、补拉及错误重试。
- `application/market.py`：原始数据与完整帧的应用命令、组帧和连续进度；`application/ledger.py` 继续负责唯一写入和事务编排。
- `storage/migrations/003_market.sql`：运行场景与应用游标、原始帧、事件发生/检测信息；`storage/sqlite.py` 实现事务。
- `api/market.py`：行情源状态查询；原风险事件 API 增加追踪信息。

启动恢复会核对冻结业务场景、原始帧摘要与内容、已应用帧和交易日志、风险事件追踪记录。场景改变、已应用原始帧缺失或游标不一致时拒绝恢复。端口、超时、故障窗口等传输设置可变更，不改写历史价格事实；已有双源运行不能通过删除行情配置切换为手工注入。

## 启动与验收

仓库根目录运行：

```bash
# 两次独立临时运行：连续接入与故障接入，结束后清理进程和数据
make demo-market

# 新建双源中断与两日日结展示：后端 8003，源端口 8201 和 8202
make run-sources

# 打包后执行同一真实 HTTP 验收
make package
uv run --project backend --locked python scripts/demo_market.py --packaged
```

手工展示从 [settlement-demo.yaml](../configs/settlement-demo.yaml) 创建独立运行，数据位于 `var/source-runs/`。后端自动管理两个源，发布包用自身的 `market-source` 子命令启动子进程，运行不依赖系统 Python。

访问 [API 文档](http://127.0.0.1:8003/api/docs)，通过 `GET /api/market/sources` 查看源连接、接收数量、连续进度、应用进度及不可交易原因；`GET /api/market` 查看完整价格，`GET /api/risk-events` 查看原发生帧和恢复发现信息。订单继续使用本地会话令牌与既有 `/api/orders` 接口。双源模式禁用 `/api/simulation/frames`，防止覆盖自动行情。

固定补数自动验收共 64 帧、约 16 秒；手工展示使用上面的两日日结场景，共 96 帧、约 24 秒：

- A 源第 8 至 20 帧不可用；第 10 帧螺纹钢从 3500 跌到 3300，第 15 帧反弹。账户 A 多仓 2 手、乘数 10，浮亏 4000 元，超过初始资金 100000 元的 3%；补数时在第 10 帧熔断。
- B 源第 30 至 40 帧不可用；第 32 帧铁矿石从 800 涨到 840，第 36 帧回落。账户 B 空仓 2 手、乘数 100，浮亏 8000 元，超过初始资金 200000 元的 3%；补数时在第 32 帧熔断。

自动验收脚本为缩短运行时间采用每帧 200 ms，业务价格和序号不变。它实际启动后端和两个 HTTP 源，验证断线时拒绝开平仓、后端被强制结束后恢复、B 源单独退出后自动重启、缺口补齐后恢复交易，以及场景结束后的持久化恢复。两源各有 64 条原始帧，连续与故障运行的账本、最终风险和业务事件一致；各自的绝对发生时间、检测时间及恢复标记另行校验。

受控时钟与临时 SQLite 的 23 项集成测试覆盖各源独立故障、两个故障窗口、错误身份/摘要、超时、不完整历史、有限范围、末帧故障恢复、原始数据缓存后重启、事务回滚、损坏数据拒绝恢复及配置冻结。具体结果维护在[测试方案](测试方案.md)。

## 当前边界与下一步

固定补数验收与[两日日结场景](日结与风控日报.md)通过显式会话边界自动清算和结转，行情序号仍贯穿整个运行。重复自动核对使用 `make demo-market`；手工展示使用 `make run-sources`，每次自动建立新数据库与运行标识。
